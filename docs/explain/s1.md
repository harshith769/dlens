# Explain: S1, the vector-RAG baseline (`eval/systems/s1.py`, S11, v0.3 D2)

Design and owner decisions: `docs/plans/s1-design.md` (B1–B9, approved 20 Oct 2026).

## What it does

S1 answers each dev question the way a plain RAG system over a dbt repo would. It searches the
project's own text, packs the best chunks into one prompt and asks the model once. It never sees
DLens's lineage graph, and there is no validator. It is the "baseline to beat" in the v0.3 resume
line, so it gets the same model, the same 3K input cap, the same answer schema and the same scoring
as S4.

```
question ─► hybrid search (BM25 + dense + RRF, all chunk kinds) ─► ≤200 ranked chunks
        ─► skip-and-pack into 3000 − 200 est. tokens ─► one answer call (+ ≤1 JSON repair)
        ─► attach citations from the shown chunks ─► Answer ─► RunRecord + manifest
```

## How it works

- **Retrieval (B1).** The query is the raw question text. `SearchIndex.search(mode="hybrid")`
  over the S07 index: BM25 and dense lists, each cut to its top 100, fused with RRF (k = 60). All
  three chunk kinds go in (model SQL, column cards, docs). No linker.
- **No graph facts.** A chunk is rendered from its fields only: `id | file:lines | title`, then
  its text verbatim. Chunk `meta` (`direct_inputs`, `downstream`) is never read, and S1 never calls
  `search_docs`, whose payload adds those facts. The graph is loaded only because
  `SearchIndex.open` keys the index on it. A test rebuilds the evidence block from the shown chunk
  ids and checks it byte for byte.
- **Budget (B2, skip-and-pack).** Chunks are tried in rank order. One is added if the *actual
  messages* (system + user + schema, `estimate_tokens`) stay within `3000 − REPAIR_RESERVE (200)`;
  otherwise it is skipped and the next one tried, until the candidates run out. There is no k
  ceiling. The reserve guarantees the one repair call fits under the cap. Each record keeps
  `k_used`, the shown and skipped ranks, unused budget tokens, and `stop` (`budget_full` if
  anything was skipped, else `candidates_exhausted`).
- **Prompt (B3).** S4's answer-phase text at 776724f, byte for byte, except `e_/s_` → `c_` in the
  claims line, plus three new lines: write columns as `model.column`, `reach_verdict`, and
  `clarification_candidates`. The user template and repair text are S4's. The schema is S4's
  `DRAFT_SCHEMA` plus the two new fields. All of it is a frozen literal in `s1.py` (not imported
  from S4, so S4 edits can't move S1), pinned by a snapshot test and by sha256 in every manifest.
- **Citations (B4).** The ledger is only the chunks shown in this prompt.
  `dlens.retrieval.citation.chunk_citation` gives each one's file/lines. A seed column card is
  cited at its CSV header line, where the column is defined (owner decision, before any run). A
  YAML description is cited from its entry's `- name:` line, so the cited lines name the column
  or model (B8 freeze change after a citation audit; S1 re-run). The evidence header shows that
  same range.
  `answer.attach` attaches them. An id the model cites but was never shown stays in the claim
  without a citation; nothing is dropped.
- **Refusal, clarification, verdict (B5, ADR 0024).** `refused` comes from the draft. A non-empty
  `clarification_candidates` becomes `Answer.clarification`, with no claims. `reach_verdict` comes
  from the draft, with `reach_verdict_source = "llm"`. Interpretation ("Interpreted A as B.") is
  deferred to S12's structured field.
- **JSON and retries (B6).** The schema goes through `LLMClient.chat(response_schema=…)`. A parse
  failure gets one repair call; a second failure is a refusal ("invalid answer JSON"). A
  retryable provider error gets one retry. Every call is a `Step` counted in `llm_calls`.
- **Run.** `make eval-s1`: the provider comes from `DLENS_PROVIDER` (default `ollama`), with the
  cache in `eval/cache`. Gemini, Groq, or an OpenAI-compatible URL off localhost is refused unless
  `--allow-cloud` is passed. A quota stop ends the run, and the missing questions score 0 (M12).
  Records go to `eval/runs/s1/`, with a manifest holding the prompt/schema/budget hashes and every
  retrieval setting, including the index key.

## Why this design

- **A fair, strong baseline.** The same hybrid retrieval S4 will use, the same cap, the same
  instructions and the same repair chance. A gap between S1 and S4 is then about the graph, not
  about a weaker retriever or prompt.
- **Skip-and-pack** (owner pick): within the same cap it shows more evidence than a strict top-k
  prefix, which can stop early on one large SQL chunk. Rank order is kept.
- **Frozen literal, not an import**: S12 will change S4's prompt. If S1 imported it, S1 would
  change too, and its numbers would no longer be the ones that were frozen.
- **The repair reserve** exists because a full prompt plus a repair turn would exceed the cap
  and turn every parse failure into a refusal.

## Alternatives rejected

- Dense-only retrieval (a weaker strawman); a rewritten query or the linker (makes S1 part DLens).
- A k ceiling (an arbitrary number, or a tuned one).
- A ledger of every retrieved chunk (would credit ids the model never saw); dropping unknown ids (a
  mini-validator S1 must not have).
- Using `search_docs` for evidence (its payload carries graph facts).

## Explain-back questions
1. A teammate swaps `render_chunk` to use the `search_docs` payload "for consistency with S4".
   What would S1 now see that it must not, and which test fails?
2. Chunk ranks 1–3 fit, rank 4 is a 270-token SQL chunk that doesn't, and ranks 5–30 are 40-token
   cards. What do strict-prefix and skip-and-pack each show, and what do `stop` and
   `unused_budget_tokens` record in each case?
3. Why does `REPAIR_RESERVE` exist, and what exactly would happen on a JSON parse failure without
   it? Why is it 200 and not 161?
