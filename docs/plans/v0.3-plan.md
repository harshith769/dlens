# DLens v0.3 plan: benchmark-ready, and works on your own project

**Version:** plan v1, 4 Oct 2026. **Applies to:** spec v1.5 → v1.6 (see `spec-delta-v1.6.md`).
**Due:** v0.3.0 by Sun 29 Nov 2026. Test-set freeze Mon 7 Dec 2026. v1.0 Sun 3 Jan 2027. Hard stop for the v1.0 benchmark: Sun 7 Feb 2027 (product releases after it are optional).
**Where this sits:** v0.1 (lineage CLI, PyPI 3 Oct) and v0.2 (cited agent + live demo, PyPI 4 Oct) are shipped. v0.3 is the bridge between "a working demo" and "a benchmarked tool real people can run on their own dbt project".

---

## 1. What we learned in v0.1–v0.2, and what it changes

The original rule book (spec v1.1) was written before any code existed. Execution taught us the following. Each row is a change this plan makes.

| # | Spec assumption | What actually happened | Change in v0.3 onward |
|---|---|---|---|
| 1 | ~197 h of solo work at 12–15 h/week; effort planned in hours | Claude Code built v0.1 and v0.2 in about two days of sessions | Plan by **gates**, not hours. The binding limits are: owner review time, Gemini quota days, and Claude Code usage limits. Spare capacity goes to a product track (Section 4) |
| 2 | Owner hand-writes `lineage/`, validator rules, linker scorer, `metrics.py` | AI writes all code; owner approves plans, reviews, and learns from `docs/explain/` | **Ownership model v2** (Section 6): owner owns design, gold data and acceptance; passes an **explain gate** before each tag |
| 3 | Local model Qwen3-8B | The Qwen3 thinking build leaked reasoning; switched to `qwen3:4b-instruct-2507-q4_K_M` (3.9 GB, 100% GPU, ~62 tok/s) | The benchmark's second model is the 4B instruct model. Record as ADR if not already |
| 4 | Validator = 4 rules; answer `confidence` field | R1–R9 plus R2r (id repair), R8c (path completion), regenerate once, then salvage. `confidence` is never used | Report S4 three ways: **raw** (pre-validator), **validated**, **augmented** (Section 3, G1). The no-validator ablation uses raw drafts |
| 5 | The LLM finds and picks the evidence | The wins came from code: chain trace, reachability facts (`r_`), unknown-column refusal (0 LLM calls), ambiguity policy | Principle: **code guarantees, the LLM narrates.** New: coverage completion for multi-input columns (dev-11, dev-20 failures) |
| 6 | Groq SDK adapter for cross-check and judge | Not built yet; real users will want their own provider | One **OpenAI-compatible adapter** (covers Groq, OpenRouter, LM Studio, vLLM, OpenAI) instead of a Groq-only SDK |
| 7 | "Live demo answers 20 dev questions" | Impossible under a 50 calls/day cap; presets + live caps shipped instead | Done; criterion amended (spec change-log row 20) |
| 8 | Runtime is dbt-duckdb; we run `dbt compile` | Real users are on Snowflake, BigQuery, Postgres, Databricks, Redshift and already have `target/` artifacts | **Artifact-only ingest, any sqlglot dialect.** Still dbt-only scope; no warehouse credentials needed |
| 9 | Streamlit UI is the demo | The UI is good; it only runs on our bundled corpus | `dlens ui --project <dir>` on any ingested project; LLM optional |
| 10 | Yes/no questions scored by edge recall | dev-10 was a correct "No" with nothing to cite, so recall punished it | Yes/no scored on **verdict accuracy** |
| 11 | One question = one intent | "Where does X come from? Can I remove it?" → the validator silently dropped the second part | **Multi-part handling**: answer what is answerable, say what isn't and suggest the right question |
| 12 | Two sources of truth: design spec, parser audit | Both the spec and the parser are now AI-written, so independence must be shown | Add a third, **dynamic** check: the **perturbation oracle** (Section 3, A4) |
| 13 | PyPI package `dlens-lineage` | `dlens` on PyPI is someone else's project | Always write `dlens-lineage` in docs; the CLI is still `dlens` |
| 14 | LanceDB for dense vectors | Corpora are 400–20,000 column cards; exact search in numpy is milliseconds | **numpy exact search** (`.npy` on disk), LanceDB dropped (ADR). Fewer deps for real users |
| 15 | Embeddings on GPU | Ollama keeps the 6 GB GPU busy | Embeddings run on **CPU** (bge-small is fast enough); install the CPU torch wheel in the `retrieval` extra |
| 16 | Agent/validator may change until the end | Rules kept changing during dev (R2r, R8c and R9 were all added after the first version) | **System freeze** with the test freeze on 7 Dec: prompts, validator version, model IDs and tool code are hashed in the run manifest |

## 2. v0.3 goal and "done when"

**Goal:** the benchmark can run end to end on the dev split, and a real analytics engineer can point DLens at their own project.

**v0.3.0 is done when all of these are true:**
1. `synthetic_shop` v2 has 40–60 models, all 9 traps, and ≥ 40 columns at 6+ hops; `dbt build` passes; the gold spec checker passes.
2. Direct-edge F1 ≥ 0.95 and **indirect-edge F1 ≥ 0.90** against the gold spec.
3. The perturbation oracle agrees with the gold spec (every value-level dependent it finds is in the gold downstream set), or every disagreement is explained in `corpora/synthetic_shop/ORACLE_REPORT.md`.
4. 96 dev questions exist, every one reviewed by the owner; the old 20 dev questions are included and re-tagged.
5. A committed pilot table: **S0, S1, S4** on the 96 dev questions, on **local qwen3:4b** and on **Gemini Flash-Lite**, with 95% bootstrap CIs and hop-depth breakdown, losses included.
6. `dlens ingest --artifacts <target/>` works for DuckDB, Snowflake, BigQuery and Postgres dialects (tested with transpiled corpora), and `dlens ui --project` works on any ingested project.
7. Drafts of the 224 test questions and the 60 set-E questions exist for owner review in Buffer A.
8. Explain gate passed (Section 6). README, CHANGELOG, demo rebuilt on corpus v2. Tag v0.3.0.

Resume line it unlocks (numbers only from committed output):
> Hybrid graph + retrieval reached [X] node-set F1 vs [Y] for vector-only RAG on a 96-question pilot, across a cloud and a local LLM.

## 3. Work items

Priority: **M** = must for v0.3.0, **S** = should, **C** = could (drop first if late).
Owner gate: what the owner must decide or review before the item is accepted.

### Track A: corpus and gold truth

| ID | Item | Pri | Owner gate |
|---|---|---|---|
| A1 | **Corpus v2 design** (`corpora/synthetic_shop/DESIGN_v2.md`): model list by layer, every trap placed, a depth plan proving ≥ 40 columns at 6+ hops, 2 exposures on different marts, stale docs, near-duplicate names. **Keep every v1 model and column name** so the 20 existing dev questions, presets and demo stay valid | M | Approve the design before any SQL |
| A2 | **Gold spec + SQL generation**: `lineage_spec.yml` v2 (direct `phase: v0.1` and indirect `phase: v0.3` edges) written from the design, never from parser output; SQL generated from it; seeded data generator; `dbt build`; spec checker | M | Review every model's SQL against the design (about 4–6 h) |
| A3 | **Indirect edges** (`DEPENDS_ON_INDIRECT`: JOIN, FILTER, GROUP_BY, WINDOW, SORT, CONDITIONAL); no double counting with direct edges; golden tests per construct; gate F1 ≥ 0.90 | M | Approve the classification rules; read `docs/explain/indirect-edges.md` |
| A4 | **Perturbation oracle** (`eval/oracle/perturb.py`): for each source column, perturb values in DuckDB, re-run the compiled models, and record which output columns change. Compare with gold downstream sets. A changed column missing from gold = spec bug or SQL drift. Unchanged gold edges are expected for some FILTER/JOIN cases and are listed, not failed | M | Read the oracle report; decide each disagreement |

Why A4 matters: it is a third source of truth that neither the spec author nor the parser controls. It answers the interview question "isn't your gold biased toward your parser?" with evidence.

## 6. Ownership model v2 and the explain gate

**Claude Code writes the code.** The owner owns:
1. **Design**: every plan, ADR and design doc is approved by the owner before code.
2. **Gold data**: the corpus design, every generated model's review, every question's review, the freeze. No AI tool edits frozen files, ever.
3. **Acceptance**: the owner approves each plan and each tag.
4. **Understanding (explain gate)**: before every tag, the owner answers the explain-back questions in each changed `docs/explain/*.md` without notes. Any module the owner cannot explain is rewritten more simply or re-explained before release.

Honest interview phrasing: *"I designed DLens and its evaluation, authored and reviewed the gold data, and directed an AI coding agent to implement it under tests and code review. I can walk you through any module."*

Integrity guards, since one AI wrote both the parser and the corpus:
- The gold spec is written from the design doc before the parser is run on the new models.
- The perturbation oracle (A4) is an independent dynamic check.
- System C1 (DLens engine vs dbt-colibri on the gold spec) in v1.0 is an external check.
- Test questions are generated from the gold spec, never from parser output.

## 7. Risks for v0.3

| Risk | Mitigation | Fallback |
|---|---|---|
| Owner review time (exams, hackathons, coursework) | Gates are batched; Buffer A holds the big review | Release v0.3 on 6 Dec; freeze stays 7 Dec |
| 3K token cap breaks on 6+ hop traces in a 50-model corpus | Compact edge strings; code-initiated chain trace; `truncated` flag; path compression in the trace payload | Raise per-tool cap only for trace, measured |
| 4B local model degrades on the bigger corpus | Coverage completion and code-initiated steps carry correctness | Report it honestly; Gemini is the headline model |
| Gemini free-tier cut | Cache; local pilot first; stop at 95% | Headline on local qwen, Gemini subset (spec 11.6 cut order) |
| Retrieval install heavy (torch) | CPU wheel; `retrieval` extra only | Dense-only via a small ONNX model (ADR) |
| Spec/SQL drift in corpus v2 | Spec checker + perturbation oracle | Fix the spec, never the parser, to match |
| Scope creep from the product track | Product items never block research gates | Move E4b to v1.1; ship E2 minimal |
| Claude Code usage limits | 2–3 sessions/week; `claude --continue` after a cut-off | Shift a session to the next day |
